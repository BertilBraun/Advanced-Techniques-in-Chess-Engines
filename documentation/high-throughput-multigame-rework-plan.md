# High-throughput multi-game AlphaZero architecture and rework plan

Status: proposed architecture; implementation has not started.

This document supersedes the Go-only target architecture in
`go-first-rework-architecture.md`. The earlier document remains useful as a
record of completed work and research contracts, but its Python-driven
self-play and Go-only product boundary are not the target design.

## 1. Objective

The project objective is:

> Build the strongest from-scratch AlphaZero-style engine obtainable within a
> fixed, modest hardware and wall-clock budget.

The intended research path is:

1. use 7x7 Go for fast screening of search, model, data, and optimization
   changes;
2. use 9x9 Go for selected confirmation and comparison with published work;
3. transfer only supported findings to chess;
4. train the final chess system from scratch on approximately four RTX 4090
   GPUs, 120 GiB RAM, and 128 CPU cores for less than 48 hours.

The project is not trying to make all games share identical states, tensors,
models, losses, or targets. It is trying to make the expensive engine
infrastructure reusable while keeping the parts that are genuinely
game-specific explicit and strongly typed.

### 1.1 Meaning of "from scratch" and the final budget

The final chess training run starts from a recorded random initialization. It
does not consume pretrained weights, human games, engine games, opening books,
tablebase labels, or Stockfish evaluations as training targets. Stockfish may
provide chess rules and act as an evaluation opponent. Any restart/opening
archive used for training is generated by the project's own self-play and is
identified in the run manifest.

The final training budget is the wall-clock interval during which self-play and
optimization produce the model, capped below 48 hours on the declared
four-GPU node. Offline evaluation is accounted separately and reported. Failed
starts, profiling, and earlier research runs are development cost, not hidden
extensions of the final model's training budget.

## 2. Corrective decisions

The next implementation must follow these decisions.

1. **Chess is a first-class supported game.** It is restored from `PreRework`
   and adapted to the new contracts. Go and chess must be selectable through
   the resolved experiment configuration.
2. **C++ owns the self-play data plane.** Game progression, many simultaneous
   games, MCTS trees, selection threads, virtual loss, leaf batching, native
   inference, tree reuse, and replay emission stay in a long-lived native
   session.
3. **Inference stays in C++.** Production self-play must not perform a pybind
   callback for every evaluated leaf. LibTorch is the initial inference
   backend. Other backends may be added behind the same native contract.
4. **Python owns the control and training planes.** Python resolves
   configuration, starts and monitors native sessions, owns PyTorch autograd,
   samples replay, publishes models, evaluates experiments, and produces
   reports. It does not advance games or schedule individual searches.
5. **Generic infrastructure and game-specific learning are separate.** Search
   scheduling, inference batching, replay transport, lifecycle, and reporting
   are generic. State encodings, action mappings, legal rules, model heads,
   losses, augmentations, and auxiliary targets may be game-specific.
6. **Performance is a correctness property.** Every hot-path refactor needs a
   throughput benchmark and utilization evidence. A logically correct feature
   that reduces strength per wall-clock hour is not automatically an
   improvement.
7. **Restoration is selective.** Do not revert the legacy-removal commit
   wholesale. Restore the proven concepts and tests from `PreRework`, place
   them behind the new interfaces, and leave the Python MCTS and mixed legacy
   control code removed.

## 3. Current-state assessment

### 3.1 Preserve and improve

The following current components are useful foundations:

- typed authoring and resolved configuration;
- immutable manifests, seeds, artifact identities, and run provenance;
- the native Go rules, encoding, symmetry, and correctness tests;
- the current search-strategy definitions for fixed, progressive, mixed, FPU,
  and adaptive search;
- replay identity, model-version, and target-weight metadata;
- checkpoint authentication and crash-safe publication concepts;
- common-search paired evaluation, fixed-elapsed-time checkpoints, bootstrap
  intervals, AUC, and report generation;
- calibration traces and evidence-derived adaptive-search thresholds;
- the `PreRework` branch as a stable source for restoration.

These components may be refactored when their current shape imposes runtime
overhead or excessive complexity. Preservation means preserving the validated
capability, not every current interface.

### 3.2 Restore and generalize from `PreRework`

The following concepts should return:

- Stockfish-backed chess legality and terminal rules;
- chess history, repetition, castling, en-passant, halfmove-clock, and move
  encoding support;
- fixed-arena search trees and root/subtree reuse;
- multi-root search over many simultaneous games;
- multiple selection workers and virtual-loss collision handling;
- native leaf collection into full inference batches;
- pinned host input/output buffers;
- dedicated native inference threads and CUDA streams;
- LibTorch model loading, warm-up, inference, and model refresh;
- native inference/search timing and batch histograms;
- native evaluation using the same search and inference implementation.

The restored code must use the project PCH, configured clang-format and
clang-tidy, the integer aliases in `common.hpp`, explicit CMake targets, and
the new namespace and ownership conventions. Hardcoded chess tensor constants
must not leak into generic code.

### 3.3 Replace or remove

The following current or historical designs are not part of the target:

- per-leaf `PythonGoEvaluator` callbacks in production self-play;
- Python thread pools that progress individual games or searches;
- a separate Python inference broker in the production self-play path;
- Python MCTS;
- Go-only root configuration and runtime factories;
- full checkpoint serialization after every small optimizer quantum;
- per-step `.item()`, `.cpu()`, scalar printing, or synchronous metric
  extraction in the training loop;
- retaining every sampled UUID in Python merely to report a training step;
- model, game, replay, and lifecycle responsibilities in one large function;
- global `BOARD_C`, `BOARD_LEN`, or `ACTION_SIZE` constants in reusable native
  inference code;
- broad compatibility shims for removed legacy settings.

The Python inference broker may remain as a correctness oracle or focused
debugging adapter. It must not be the production throughput path.

### 3.4 Migration safety

The current path is not deleted merely because a replacement compiles. During
restoration:

- current and replacement implementations have distinct build targets;
- identical fixtures and benchmark inputs can run through both;
- numerical, rule, replay, and search parity differences are recorded;
- the replacement becomes default only after its stage acceptance gates pass;
- obsolete code is removed in a later, separate commit with an explicit
  capability map.

### 3.5 Measured maintainability debt

At the time of this plan, notable Python production functions include:

- `run_training_window`: 261 lines;
- `run_go_worker`: 197 lines;
- `build_runtime_plan`: 185 lines;
- `_play_game`: 173 lines;
- `RuntimeOrchestrator.run`: 154 lines.

The architecture below eliminates the Python self-play functions rather than
splitting an inherently misplaced hot path into more Python functions.

## 4. System boundaries

The system has four major planes.

```text
+--------------------------------------------------------------------+
| Python experiment control plane                                    |
| config, manifests, supervision, checkpoints, reports               |
+--------------------------------+-----------------------------------+
                                 | coarse commands/artifacts
+--------------------------------v-----------------------------------+
| Native C++ self-play/evaluation data plane                         |
| games, MCTS, leaf batching, LibTorch inference, replay shards      |
+--------------------------------+-----------------------------------+
                                 | versioned binary replay
+--------------------------------v-----------------------------------+
| Python/PyTorch training plane                                      |
| replay loading, augmentation, DDP, losses, model publication       |
+--------------------------------+-----------------------------------+
                                 | immutable model generation
+--------------------------------v-----------------------------------+
| Evaluation and research plane                                      |
| native matches, common search, statistics, ablation reports        |
+--------------------------------------------------------------------+
```

Communication across a boundary is coarse-grained:

- resolved session configuration at process/session start;
- immutable model-generation publication;
- replay shards containing complete positions or games;
- periodic aggregate telemetry;
- stop, drain, refresh, and health commands.

Individual inference requests, leaf selections, moves, and games do not cross
the Python boundary.

### 4.1 Production deployment form

The production self-play unit is a long-lived native executable, initially
`az_selfplay_worker`, with one process per assigned inference GPU. Python starts
it with an immutable resolved session file and supervises its exit status.
Control uses coarse, authenticated messages or atomic control artifacts for:

- stop and drain;
- model-generation availability;
- health and progress;
- replay-shard publication;
- aggregate telemetry.

A pybind session facade may exist for correctness tests, microbenchmarks, and
interactive debugging. It calls the same C++ session implementation and must
not become a second production scheduler.

### 4.2 Target source layout and dependency direction

```text
cpp/
|-- src/core/                 identifiers, seeds, small utilities
|-- src/games/go/             Go rules, encoding, policy map, replay codec
|-- src/games/chess/          chess rules/history, encoding, policy map, codec
|-- src/search/               generic trees and search policies
|-- src/inference/            LibTorch backend, buffers, model generations
|-- src/self_play/            multi-game scheduler and game lifecycle
|-- src/replay/               shard container, writer, checksums
|-- src/runtime/              session factory and coarse control protocol
|-- src/apps/                 self-play, evaluation, and UCI executables
|-- src/bindings/             test/debug Python facade only
|-- test/
`-- benchmark/

py/src/az/
|-- config/                   authoring, resolution, manifests
|-- games/go/                 Go model, objective, batch/augmentation
|-- games/chess/              chess model, objective, batch/augmentation
|-- models/                   shared neural building blocks
|-- replay/                   catalog, sampling, native shard readers
|-- training/                 persistent generic DDP trainer
|-- runtime/                  native-process supervision
|-- evaluation/               match plans and statistics
|-- experiments/              lifecycle, feature registry, matrices
`-- reporting/                evidence assembly and rendering
```

Dependencies point inward:

- game modules depend on core, not search, inference, or orchestration;
- search depends on the game concept, not concrete Go/chess modules;
- inference knows tensor/artifact contracts, not game rules;
- self-play composes game, search, inference, and replay;
- native applications depend on runtime/session factories;
- Python training depends on typed game-training modules, never native
  self-play internals;
- reporting consumes evidence models and never imports runtime workers.

Circular dependencies and convenience imports across these boundaries are
architecture failures, not cleanup tasks for later.

## 5. Native game architecture

### 5.1 Compile-time game specialization

The hot native engine is statically specialized by game. Runtime configuration
selects one already-compiled specialization at the outer boundary.

Conceptually:

```cpp
template <GameDefinition Game>
class SelfPlaySession;

using Session = std::variant<
    SelfPlaySession<GoDefinition>,
    SelfPlaySession<ChessDefinition>>;
```

Templates or equivalent static polymorphism are used inside MCTS, encoding,
and replay generation so node traversal does not pay for virtual dispatch.
`std::variant`, a small factory, or a type-erased session interface is allowed
only at process/session creation and control boundaries.

### 5.2 `GameDefinition` contract

Each game specialization explicitly owns:

- `State`, `Action`, `Rules`, `Player`, `TerminalResult`, and
  `TerminationReason`;
- legal-action generation and state mutation;
- state equality and search/transposition keys;
- current-player terminal value;
- canonical input encoding shape and dtype;
- policy-space size and action-to-policy mapping;
- inverse policy mapping for selected actions;
- valid symmetries and action/encoding transformations;
- replay payload encoding and schema version;
- optional game-specific diagnostic fields.

The contract supports dynamic Go board sizes without making tensor shapes
dynamic within one session. A Go session is created for one configured size,
such as 7x7 or 9x9. Chess has its fixed board and policy layout.

### 5.3 Go specialization

The current native Go implementation is retained and adapted to the complete
contract. Board sizes of at least 3 remain legal when the action space fits the
native signed action type. Experimental profiles use 7x7 and 9x9.

The primary rules profile remains explicit:

- area scoring;
- positional superko;
- illegal suicide;
- configured komi;
- two passes terminate;
- safety-ply termination is diagnostic and is never mislabeled as a normal
  draw.

### 5.4 Chess specialization

Chess is restored using the pinned Stockfish rules dependency from
`PreRework`. The first restored version preserves the previously tested
encoding and policy map to avoid combining rules restoration with a learning
representation experiment.

The chess state contract includes enough history to handle:

- repetition rules as configured;
- the fifty/seventy-five move rules;
- castling rights;
- en-passant legality;
- side to move;
- terminal checkmate, stalemate, insufficient material, and rule draws.

Search keys distinguish position identity from history-dependent game state.
Any transposition sharing must prove that its key contains all information
needed for legality and value semantics.

## 6. Native search and self-play data plane

### 6.1 Per-device worker group

One native worker group is created per self-play GPU. A worker group owns:

- one loaded model generation per inference replica;
- a configurable number of CPU selection threads;
- a large pool of simultaneous games;
- one search tree per active game;
- one shared inference service;
- pinned staging slots;
- replay shard writers;
- aggregate telemetry.

The initial implementation uses one model replica and one batching service per
GPU. Multiple inference lanes or CUDA streams are a configuration option to
benchmark, not a reason to duplicate the model by default.

### 6.2 Multi-game scheduler

The scheduler operates over many roots and keeps selection work available
while inference batches are running. It:

1. chooses a schedulable root fairly;
2. selects a leaf and applies virtual loss;
3. writes the canonical encoding directly into a pinned batch slot;
4. submits a full batch or a latency-bounded partial batch;
5. processes completed policy/value tensors;
6. expands and backs up leaves;
7. detects search completion and advances games;
8. reuses the selected subtree when enabled;
9. immediately schedules replacement work.

Search-thread count, active-game count, leaf concurrency per root, batch size,
maximum batch wait, outstanding slots, and CUDA stream count are independent
configuration values.

### 6.3 Inference service

The initial backend is a generalized form of `DirectInferencePipeline`:

- LibTorch loads an exported inference artifact;
- input/output shapes come from selected game/model artifact metadata;
- pinned CPU slots and preallocated device buffers are reused;
- host-to-device copies are nonblocking where supported;
- inference runs under `torch::InferenceMode`;
- BF16 or FP16 is selected explicitly;
- output processing stays native;
- model refresh is prepare/warm/validate, drain, then atomic generation swap;
- no Python callback is involved.

The backend interface may later support TorchScript optimization,
`torch.compile`/AOT export where practical, CUDA graphs, TensorRT, and INT8.
Those are backend ablations. The search scheduler does not depend on one.

The initial inference artifact is TorchScript because it is already compatible
with LibTorch and the restored pipeline. Every artifact carries:

- game/model family and schema versions;
- input shape, dtype, and layout;
- named output heads with shapes and semantics;
- policy-space identity;
- training checkpoint and model-generation identity;
- content checksum.

Publishing fails unless the exported artifact passes a native warm-up and
shape/semantic validation for its declared game session.

### 6.4 Search strategy composition

Search behavior is composed from typed policies rather than one monolithic
mode:

- budget policy: fixed, progressive, mixed fast/full, or position-adaptive;
- candidate policy: all legal, top-k, sequential halving, or Gumbel sampled;
- selection policy: PUCT or transformed/completed-Q variants;
- FPU policy;
- root exploration policy;
- stopping policy;
- policy-target construction and pruning policy;
- tree-reuse policy;
- optional transposition policy.

Unsupported combinations fail during configuration resolution. Search
telemetry records both configured and actual behavior.

### 6.5 Native replay emission

Completed native games are written directly to versioned binary replay shards.
The generic shard envelope includes:

- game identifier and game-specific payload schema;
- run/config/model identities;
- game and position identifiers;
- deterministic seed lineage;
- model generation;
- state/action/policy/value targets;
- actual simulations, budget class, stop reason, and policy weight;
- terminal result and termination category;
- optional feature-specific targets;
- checksums and atomic publication metadata.

The payload is a discriminated game-specific record. Go and chess do not force
their tensors or auxiliary fields into one nullable structure. JSON and
per-position pybind object construction are excluded from production replay.

## 7. Training plane

### 7.1 Game training modules

The generic trainer depends on a game training module selected by the resolved
game/model configuration. A module owns:

- model construction;
- replay decoding into typed batches;
- augmentation;
- forward outputs;
- primary and auxiliary losses;
- inference artifact export;
- game-specific metrics evaluated outside the hot loop.

Go and chess may have different networks, policy heads, value heads, auxiliary
heads, losses, and batch types. Shared residual/global-pooling blocks live in a
model component library rather than in a fake universal model.

### 7.2 Persistent high-throughput loop

Training ranks are long-lived. The normal optimizer loop contains only:

1. obtain a prefetched pinned batch;
2. nonblocking transfer to the assigned GPU;
3. forward under the configured autocast mode;
4. calculate tensor losses;
5. backward;
6. optional gradient clipping;
7. optimizer/scaler/scheduler step;
8. update device-resident metric accumulators.

The loop must not:

- call `.item()` or copy loss tensors to CPU per step;
- append Python floats or sample UUID tuples per step;
- serialize a checkpoint per optimizer quantum;
- rebuild the model, optimizer, sampler, replay catalog, or process group;
- scan replay directories;
- log synchronously.

Finite-loss checks use a device-side flag accumulated over an interval and
synchronize only at an explicit safety/telemetry boundary.

### 7.3 Metrics without per-step synchronization

Loss sums, sample counts, gradient statistics, and other inexpensive metrics
remain tensors on device. At a configured interval:

- ranks reduce one compact metric tensor;
- rank zero copies it to CPU once;
- reporting consumes the aggregate;
- expensive diagnostic slices run on sampled batches or evaluation jobs.

Per-step detailed provenance comes from replay/sampler journals, not Python
lists in the optimizer loop.

### 7.4 Replay pipeline

Replay loading uses an incremental index, memory mapping or sequential shard
reads, persistent loader workers, bounded prefetch, pinned host batches,
vectorized decoding/augmentation, and explicit target age/model generation.
Uniform recent replay is the initial baseline.

Prioritized replay, recency weighting, deduplication, reanalysis, and growing
windows are later strategies behind the sampler contract.

### 7.5 Checkpoint and model publication cadence

Three cadences are separate:

1. **optimizer progress commit:** small durable state needed to account for
   replay consumption;
2. **training checkpoint:** model, optimizer, scaler, RNG, sampler, and
   scheduler state for restart;
3. **self-play model publication:** immutable inference artifact consumed by
   native workers.

No cadence implicitly forces the others. Checkpoints and inference exports are
published every configured number of steps or seconds, not after every small
credit quantum. Serialization is staged outside the tight optimizer loop and
measured separately.

## 8. Configuration model

The root configuration is a frozen discriminated union:

```text
ExperimentConfiguration
|-- game: GoGameConfiguration | ChessGameConfiguration
|-- model: GoModelConfiguration | ChessModelConfiguration
|-- objective: GoObjectiveConfiguration | ChessObjectiveConfiguration
|-- search: composed native search policies
|-- self_play: native worker groups and topology
|-- replay: storage and sampling
|-- training: optimizer/DDP/cadences
|-- evaluation: opponents/search/checkpoints
`-- telemetry/retention/research metadata
```

Resolution validates compatible triples of game, model, and objective.
Infrastructure is shared only where its semantics are genuinely identical.
The native session receives a compact, versioned resolved configuration; it
does not parse Python class names or unvalidated string keys.

### 8.1 Feature registry

`THINGS_TO_TRY.md` remains the idea inbox. An idea is not implemented directly
from prose. Before implementation it is promoted to a typed feature record
with:

- stable feature ID and owner layer;
- generic, Go-only, or chess-only scope;
- configuration type and default-disabled baseline behavior;
- prerequisites and incompatible features;
- required telemetry;
- screening and confirmation protocol;
- implementation and experiment status;
- links to result artifacts, including neutral or negative results.

This registry prevents config options, implementations, and experiment claims
from drifting apart. Population-based or automated hyperparameter optimization
may propose screening candidates only after the baseline is stable; it does
not replace held-out confirmatory runs.

## 9. Process and hardware topology

The system supports:

- **exclusive:** separate GPUs for self-play inference and DDP training;
- **colocated:** training and inference share GPUs with explicit streams and
  measured contention;
- **phased:** bounded self-play and training bursts use all GPUs in turn.

The final topology is selected by strength per wall-clock hour. For the planned
four-RTX-4090 node, initial candidates are two inference plus two DDP GPUs, one
inference plus three DDP GPUs, four colocated GPUs, and short all-GPU phased
bursts.

The 128 CPU cores feed native search and replay decoding. CPU affinity, NUMA
placement, pinned-memory pressure, and worker counts are recorded and
benchmarked.

## 10. Evaluation methodology

### 10.1 Primary objective and metrics

All comparisons use identical hardware and training wall time. Primary metrics:

- learning-curve AUC against wall-clock time;
- final Elo or paired win rate at fixed time;
- strength gained per hour.

Required operational metrics:

- games and positions per hour;
- simulations and evaluated leaves per second;
- inference batch-size distribution, latency, and queue wait;
- GPU utilization and memory;
- CPU utilization and search-thread idle time;
- optimizer steps and samples per hour;
- replay reuse, age, and target model age;
- checkpoint/model-publication overhead;
- actual simulations and early-stop rates.

### 10.2 Experiment tiers

**Tier A: engineering validation**

- correctness fixtures and throughput microbenchmarks;
- short native integration runs;
- no playing-strength claim.

**Tier B: 7x7 Go screening**

- fixed hardware/duration, matched initialization and seeds;
- normally three seeds;
- common evaluation search;
- promote only credible strength-per-hour improvements without unexplained
  correctness or utilization regressions.

**Tier C: confirmation**

- 5-10 7x7 seeds where affordable;
- selected 9x9 confirmation;
- bounded chess transfer pilots;
- final chess run only for the selected system.

### 10.3 Transfer policy

A Go improvement is not assumed to transfer to chess.

- Generic changes are screened on 7x7.
- Strong scale-sensitive candidates are checked on 9x9.
- Each selected change receives a bounded chess pilot or is disabled.
- Chess-specific features are evaluated only on chess.

Reports distinguish demonstrated Go improvements, demonstrated chess
improvements, and transferred components without isolated chess confirmation.

### 10.4 Chess evaluation and play

Chess evaluation uses the same native search/inference session as self-play,
with exploration disabled and an explicit evaluation search configuration.
Reference opponents include fixed archived project checkpoints and pinned
Stockfish configurations. Color and opening assignments are paired.

A UCI executable is restored only after the native chess session is stable. It
is a thin protocol adapter over the same chess search/inference implementation,
not a separate engine or search tree.

## 11. Feature roadmap from `THINGS_TO_TRY.md`

The architecture exposes extension points for the complete backlog without
implementing every feature immediately.

### 11.1 First confirmatory sequence

1. progressive simulation budget;
2. mixed fast/full search;
3. adaptive termination calibrated from full-search traces;
4. FPU variants;
5. optimizer-to-data ratio;
6. replay-window size;
7. model-publication cadence;
8. progressive model scaling;
9. global-context blocks;
10. generic auxiliary heads.

The first comparison remains:

```text
fixed vs progressive vs mixed fast/full vs adaptive stopping
```

FPU and model scaling follow only after search-compute is stable.

### 11.2 Search extension point

Forced playouts/target pruning, Gumbel sampling, deterministic sequential
halving, completed/transformed Q, dynamic candidate counts and position
budgets, tree reuse, transpositions, batching, and virtual loss.

### 11.3 Data-generation extension point

Restart states, branching, difficult-state prioritization, reanalysis,
resignation, opening diversity, position filtering, and game-specific
draw/repetition handling.

### 11.4 Model/objective extension point

Generic heads: opponent policy, remaining length, future action, return
distribution, root Q, outcome type, multi-horizon value, and uncertainty.

Chess-only heads: material, survival/capture, king safety, terminal distance,
attack/control maps, and legal actions. Chess-only supervision is excluded from
the primary minimal-knowledge method unless an explicit upper-bound ablation
enables it.

### 11.5 Architecture, optimization, replay, and augmentation

Extension points cover global pooling/squeeze-excitation, width/depth
schedules, separated trunks, hybrid/transformer models, efficient layouts,
quantization, compile/AOT/CUDA graphs, precision, optimizer/LR schedules,
EMA/SWA, accumulation, loss balancing, prioritized/recency replay,
deduplication, freshness tracking, exact symmetries, player canonicalization,
valid color swapping, and target smoothing.

Go and chess declare valid transformations independently. Chess
transformations update castling, en-passant, history, and action encoding.

## 12. Code-quality and performance gates

### 12.1 Maintainability

Default production-code limits:

- Python function: at most 80 logical lines;
- C++ function: at most 100 logical lines;
- nesting depth: at most 4;
- cyclomatic complexity: at most 15;
- source file target: at most 500 lines.

Declarative binding/configuration tables and proven hot loops may receive a
reviewed, documented exception. Python uses Ruff complexity rules plus an
AST-based size/nesting test. C++ uses clang-tidy function-size and complexity
checks. Every stage runs formatting, static checks, and relevant tests.

### 12.2 Hot-path review

Every hot-path change answers:

- Does it synchronize CUDA or acquire the GIL?
- Does it allocate per leaf, position, or optimizer step?
- Does it serialize/hash large state or scan directories synchronously?
- Does it copy tensors to CPU?
- Does it add virtual dispatch inside node traversal?
- Which benchmark detects regression?

### 12.3 Benchmark gates

Before replacing a proven `PreRework` component, capture its benchmark on the
same machine. A replacement needs equal/better evaluated positions per second,
equal/better games per hour, or equal/better strength per hour despite a
measured throughput cost.

Native benchmarks cover rules, encoding, selection/expansion/backup, batch
assembly, inference by batch size, and complete self-play. Training benchmarks
cover decoding, copy overlap, steps/second, checkpoint/publication pauses, and
GPU utilization.

## 13. Staged implementation plan

Each stage is committed only after acceptance passes.

### Stage 0: freeze evidence and benchmark both designs

- Keep `PreRework` immutable.
- Benchmark its direct inference and multi-root search.
- Benchmark the current callback path and trainer.
- Record throughput, utilization, latency, memory, and model shapes.

Acceptance: commands and schemas are reproducible; restoration targets are
numerical; no strength claim is made.

### Stage 1: native multi-game contracts and build structure

- Add `GameDefinition`, artifact metadata, and native session config.
- Split explicit core, Go, chess, inference, self-play, binding, executable,
  test, and benchmark CMake targets.
- Use static specialization in hot loops and runtime selection at the factory.
- Add maintainability gates.

Acceptance: a toy game plus Go instantiate contracts; no Python evaluator is
required; compile commands cover targets; clang-format/tidy pass.

### Stage 2: restore chess correctly

- Restore pinned Stockfish and patch.
- Port board/history, encoding, action mapping, terminal outcomes, and tests.
- Add differential legality and repetition/rule-draw/castling/en-passant/
  promotion fixtures.

Acceptance: typed config selects Go or chess; both instantiate native
contracts; chess parity passes; search/inference is not duplicated by game.

### Stage 3: restore and generalize native LibTorch inference

- Port `DirectInferenceRunner/Pipeline`.
- Replace globals with artifact/session metadata and specialized tensor
  contracts.
- Add pinned slots, one model replica/device, streams, warm-up, refresh, and
  failure propagation.
- Export artifacts from Go and chess modules.

Acceptance: zero Python calls per leaf; numerical parity for both games;
equivalent chess throughput meets the captured reference or has an approved
explanation; refresh is atomic.

### Stage 4: generic batched MCTS and native self-play

- Port fixed arenas, multi-root scheduling, virtual loss, batching, tree reuse.
- Integrate fixed/progressive/mixed/adaptive/FPU strategies.
- Move game progression and target production into C++.
- Add coarse start/stop/drain/status/refresh control.

Acceptance: no Python game pool/inference broker in production; both games run
many simultaneous games; deterministic search matches fixtures; no stranded
virtual loss; throughput meets Stage 0.

### Stage 5: versioned native replay transport

- Add generic envelope plus Go/chess payloads.
- Write atomic binary shards and a compact index.
- Add checksums, model/seed/search evidence, and vectorized pinned decoding.

Acceptance: exact round trips; torn/corrupt data is safe; no per-position
pybind objects; decoding keeps training fed.

### Stage 6: rebuild the trainer hot path

- Use a persistent loop.
- Remove per-step `.item()`, CPU loss copies, UUID lists, and sync logs.
- Add device metrics, persistent loaders, prefetch, nonblocking copies, DDP,
  BF16, and optional layout/compile modes.
- Separate progress, restart checkpoint, and inference-publication cadences.
- Enforce maintainability limits.

Acceptance: profiler shows no unintended step synchronization; throughput and
utilization meet targets; restart state is complete; publication pauses are
reported; Go/chess share the trainer loop.
